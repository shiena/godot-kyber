# H.264映像を使う

[English](h264.md) · [映像ガイド](video_ja.md)

動画ファイルとViewportの送信で、H.264を選択できます。既定値はJPEGです。受信側は配信のコーデックヘッダーからデコーダーを選びます。

## デモでH.264を試す

1. [映像ガイド](video_ja.md#godotからデモを起動する)の手順で、Godotからデモを2つ起動します。
2. 片方で［Sender］を選択します。
3. 送信開始前に［H.264 (requires receiver support)］を選択します。
4. 初回は［H.264 acceleration: Auto］を選択します。
5. 動画を開き、［Start streaming］をクリックします。
6. 送信側のアドレス・ポート・接続コードで受信側を接続します。

受信映像が更新されることを確認します。初期化に失敗した場合は状態表示を確認し、JPEGでも試して接続とコーデックの問題を切り分けます。Autoではソフトウェアに切り替わる場合があるため、接続の成功だけではハードウェア処理を使用していると判断できません。

## コーデックを選ぶ

`KyberFileVideo`の開始前に設定します。

```gdscript
video.video_codec = 1 # 0: JPEG, 1: H.264
video.acceleration = 0 # 0: Auto, 1: Software, 2: HardwareRequired
video.start_sender(path, "0.0.0.0", 4433, true)
```

`KyberSession`で受信する場合は、`start_receiver()`の前に`session.acceleration`を設定します。`KyberFileVideo`で直接受信する場合は、そのノードの`acceleration`を使います。これらはアドオンのファイル・Viewport配信用設定です。`KyberClient`による既存ホストへの要求には適用しません。

動画ファイルデモにも同じ選択肢があります。受信側で送信形式を合わせる操作は不要ですが、H.264デコーダーが必要です。対応形式の交渉や、JPEGとH.264の自動切り替えは未実装です。JPEGだけに対応する旧版アドオンは、H.264配信を拒否します。

## 高速化の方法を選ぶ

| 値 | 動作 |
|---|---|
| `0` — Auto | ハードウェア経路を試し、初期化時にソフトウェアへフォールバック。AndroidはMediaCodecに選択を委任 |
| `1` — Software | ソフトウェアコーデックを要求。OSが提供しない場合はエラー |
| `2` — HardwareRequired | ハードウェア処理を必須に指定。利用不可・判定不可の場合はエラー |

H.264への対応と、ハードウェアによる高速化は別の条件です。`get_media_capabilities().h264_encode`は、アドオンに符号化バックエンドが含まれることを示します。コーデックやGPUドライバーのインストールを保証しません。実行時の失敗は配信開始時に通知します。

Androidでは、対応する全APIレベルで高速化の有無を確実に判定できません。AutoまたはSoftwareを使います。HardwareRequiredは、この制限をエラーとして通知します。

| プラットフォーム | 符号化・復号の実装 |
|---|---|
| Windows | Media Foundation。ハードウェアエンコーダーMFT、D3D11復号、ソフトウェア経路 |
| macOS／iOS | VideoToolbox。利用可否は端末とOSに依存 |
| Linux | インストール済みのGStreamerプラグイン。VA・NVIDIAの候補と、`x264enc`・`openh264enc`のソフトウェア候補 |
| Android | MediaCodec。CPU入力バッファとImageReader出力 |

Linuxでは`h264parse`、`videoconvert`、appsrc、appsinkも必要です。ハードウェア用プラグインが存在しても、GPUドライバーが使えるとは限りません。

## 初期実装の配信仕様

H.264は640×360、最大24 fps、目標ビットレート4 Mbit/sで送信します。各アクセスユニットは、パラメーターセットを含む独立したキーフレームです。最新フレームの優先、途中参加、パケット欠落からの復帰を維持します。フレーム間予測を使うGOPと同じ通信量削減は得られません。

Reliable、Unreliable、Unreliable + FECを引き続き利用できます。Opus音声と映像はKyberの共通クロックを使います。一部のGPUデコーダーが独自の時刻を返すため、受信側ではアクセスユニットの順序で元の時刻を保持します。

符号化・復号は専用ワーカーで実行します。符号化の入力画像はCPUメモリーを経由します。ハードウェア処理でCPU時間が減っても、総遅延が短くなるとは限りません。色変換、画像転送、ドライバーの待ち時間も影響します。

### WindowsのGPU受信

`KyberSession.gpu_transfer`と`KyberFileVideo.gpu_transfer`の既定値は`true`です。WindowsのD3D12とForward+／Mobileでは、復号したH.264画像をGPU上に保持できます。Godot 4.4以降が必要です。Compatibility、ほかの描画ドライバー、ほかのプラットフォームではCPU転送を使います。無効にするには`gpu_transfer = false`を設定します。Software指定時もCPU転送を使います。

GPU上でNV12からRGBAへ変換し、Godot所有のGPUテクスチャへコピーします。通常の再生ではCPUへの読み戻しを省きますが、ゼロコピーではありません。受信セッションを設定した`KyberVideoStream`は、テクスチャを`VideoStreamPlayer`と共有します。`latest_image()`を呼ぶと、明示的にCPUへ読み戻します。

`get_texture()`の戻り値を受ける変数は、`ImageTexture`ではなく`Texture2D`型にします。GPU受信時は`Texture2DRD`を返します。3Dマテリアルには、セッションのテクスチャを直接設定してください。再生リソースは、`VideoStreamPlayer`に渡すテクスチャを固定するために`CanvasTexture`を使います。

この経路が有効な場合、性能統計の`gpu_transfer`は`d3d12_shared`になります。デコーダーの初期化・復号に失敗した場合はCPU転送へ戻ります。単独の`KyberVideoStream`受信と既存ホスト受信はCPU転送を維持します。符号化用のGPU直接キャプチャと、ほかのプラットフォームのGPU共有は未実装です。

既存ホストの受信は従来のデコーダー経路を維持します。Windowsでは任意のホスト配信に対応するため、ソフトウェア経路を残しています。新しいGPU経路の検証対象は、アドオンの独立フレーム形式です。

## バックエンドを測定する

| 環境 | 今回の実装で確認済みの範囲 |
|---|---|
| Windows | ソフトウェア・ハードウェアの符号化／復号、GodotのH.264／Opus同期、FEC欠落試験、D3D12 Forward+／MobileとCompatibilityの表示・3回の再接続 |
| macOS arm64 | ソフトウェア・ハードウェアの符号化／復号、GodotのH.264／Opus同期 |
| WSL上のUbuntu | ソフトウェアの符号化／復号、GodotのH.264／Opus同期。ハードウェア高速化は利用できず |
| Android arm64 | Releaseビルド、ネイティブAuto符号化／復号、X4000とWindows間の双方向H.264／Opus送受信 |
| iOS arm64 | Releaseライブラリ、Xcodeでの署名・インストール、iPhone 15 ProとWindows間の双方向H.264／Opus送受信 |

2026年11月23日、Auto高速化・Reliable転送でモバイルのH.264／Opusテストが通りました。表は受信映像フレーム数と音声キャプチャのサンプル数です。同期差p95は音声・映像の時刻差であり、通信全体の遅延ではありません。今回は自動検証で、目視・聴取確認は含みません。

| 方向 | 映像フレーム数 | 音声サンプル数 | 同期差p95 |
|---|---:|---:|---:|
| Windows → Android | 436 | 881,664 | 16.213 ms |
| Android → Windows | 392 | 884,736 | 6.782 ms |
| Windows → iPhone | 440 | 960,512 | 8.022 ms |
| iPhone → Windows | 458 | 884,736 | 6.876 ms |

符号化用GPUキャプチャと、ほかのプラットフォームのGPU共有は未実装です。今回のモバイルテストはCPU転送を使っています。AndroidのAutoでは、ハードウェア高速化の有無を判定できません。

2026年11月23日、Android→iPhoneとiPhone→Androidも目視で確認しました。逆方向では当初Androidの表示が約11～12 fpsでした。MediaCodecの出力を最大20 ms待つように修正し、複数画像のまとめ出力とフレーム欠落を抑えました。同じテストで約20～24 fpsへ改善し、目視でも改善を確認しました。この値は使用端末での観測結果であり、保証値ではありません。

対応GPUを搭載したWindowsでは、`--path demo --rendering-method mobile --rendering-driver d3d12 --script tests/process/gpu_video.gd -- gpu`で描画テストを実行できます。CPU転送は`--rendering-method gl_compatibility`と末尾の引数`cpu`で確認します。画像の色、プレーヤーのテクスチャ読み戻し、画面出力、再接続を検証します。

```sh
cargo run --release --manifest-path media/Cargo.toml --example h264_probe -- software
cargo run --release --manifest-path media/Cargo.toml --example h264_probe -- hardware
cargo run --release --manifest-path media/Cargo.toml --example h264_probe -- auto
```

生成した120フレームを符号化・復号します。寸法、色、キーフレームを検査し、経過時間とプロセスのCPU時間を出力します。HardwareRequiredでは、バックエンドが報告する高速化の状態も検査します。AndroidのAutoではハードウェアが選ばれる場合もありますが、判定できないため`hardware_*`はfalseです。

Godotでの映像・音声同期は別に検証します。

```sh
python scripts/test_audio_processes.py --godot /absolute/path/to/Godot --codec h264 --acceleration 0
python scripts/test_audio_processes.py --godot /absolute/path/to/Godot --codec h264 --acceleration 0 --transport 2 --drop-every 11 --audio-stream
```
