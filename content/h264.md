# Use H.264 video

[日本語](h264_ja.md) · [Video guide](video.md)

The file and Viewport senders support optional H.264 encoding. JPEG remains the default. Receivers select the decoder from the incoming codec header.

## Try H.264 in the demo

1. Start two demo instances from Godot as described in the [video guide](video.md#start-the-demo-in-godot).
2. Select **Sender** in one instance.
3. Before starting, select **H.264 (requires receiver support)**.
4. Select **H.264 acceleration: Auto** for the first test.
5. Open a video and click **Start streaming**.
6. Connect the receiver with the sender's address, port, and connection code.

Confirm that the received image updates. If initialization fails, check the status message and try JPEG to separate connection problems from codec availability. Auto can fall back to software; a successful connection alone does not prove that a hardware codec is active.

## Select a codec

Set these properties before starting `KyberFileVideo`:

```gdscript
video.video_codec = 1 # 0: JPEG, 1: H.264
video.acceleration = 0 # 0: Auto, 1: Software, 2: HardwareRequired
video.start_sender(path, "0.0.0.0", 4433, true)
```

For reception through `KyberSession`, set `session.acceleration` before `start_receiver()`. A standalone `KyberFileVideo` receiver uses its own `acceleration` property. These settings apply to the addon's file/Viewport protocol, not existing-host requests through `KyberClient`.

The file demo exposes the same options. The receiver doesn't need a matching codec selection. It needs an available H.264 decoder. Codec negotiation and automatic switching between JPEG and H.264 aren't implemented. Older addon versions that support only JPEG reject an H.264 stream.

## Choose acceleration

| Value | Behavior |
|---|---|
| `0` — Auto | Try the platform's hardware path, with software fallback during initialization. Android delegates selection to MediaCodec. |
| `1` — Software | Request a software codec. Fail if the OS doesn't provide one. |
| `2` — HardwareRequired | Require hardware processing. Fail if unavailable or unverifiable. |

H.264 support and hardware acceleration are separate capabilities. `get_media_capabilities().h264_encode` indicates that the addon includes an encoder backend. It doesn't guarantee that a codec or GPU driver is installed. Starting the stream reports runtime failures. Android's backend can't verify acceleration across every supported API level; use Auto or Software there. HardwareRequired reports this limitation instead of silently using software.

| Platform | Encoder and decoder |
|---|---|
| Windows | Media Foundation; hardware encoder MFTs and D3D11 decoding, with software alternatives |
| macOS / iOS | VideoToolbox; availability depends on the device and OS |
| Linux | Installed GStreamer plugins; hardware candidates include VA and NVIDIA, with `x264enc` or `openh264enc` software alternatives |
| Android | MediaCodec; CPU input buffers and ImageReader output |

Linux also needs `h264parse`, `videoconvert`, appsrc, and appsink. Installing a hardware plugin doesn't guarantee access to a working GPU driver.

## Understand the initial transport

H.264 sends 640 × 360 video at up to 24 fps with a target bitrate of 4 Mbit/s. Every access unit is an independent keyframe with parameter sets. This preserves latest-frame delivery, late joins, and recovery after packet loss. It doesn't provide the bandwidth savings of an inter-frame GOP.

The existing Reliable, Unreliable, and Unreliable + FEC transports remain available. Opus audio uses the same Kyber clock. The receiver restores this clock's timestamps in access-unit order because some hardware decoders synthesize timestamps.

Encoding and decoding run on dedicated workers. Encoding currently accepts CPU frames. Hardware acceleration can reduce CPU time without reducing total latency; conversion, transfers, and driver queues still contribute.

### Windows GPU reception

`KyberSession.gpu_transfer` and `KyberFileVideo.gpu_transfer` default to `true`. Windows with D3D12 and Forward+ or Mobile can keep decoded H.264 frames on the GPU. This requires Godot 4.4 or later. Compatibility, other drivers, and other platforms use CPU transfer. Set `gpu_transfer = false` to disable this path. Software acceleration also disables it.

The decoder converts NV12 to RGBA on the GPU, then copies into a Godot-owned GPU texture. Normal playback avoids CPU readback, but this is not zero-copy. A `KyberVideoStream` attached to the receiving session shares the texture with `VideoStreamPlayer`. Calling `latest_image()` explicitly reads pixels back to the CPU.

Type variables that receive `get_texture()` as `Texture2D`, rather than `ImageTexture`: GPU reception returns `Texture2DRD`. For a 3D material, use the session's texture directly. The playback resource uses `CanvasTexture` to keep a stable texture for `VideoStreamPlayer`.

Performance statistics report `gpu_transfer = "d3d12_shared"` when active. Decoder initialization or decoding failures fall back to CPU transfer. Standalone `KyberVideoStream` and existing-host reception retain CPU transfer. GPU capture for encoding and GPU sharing on other platforms remain unimplemented.

Existing-host reception retains its previous decoder path. In particular, Windows keeps the software path for arbitrary host streams; the new GPU path is verified with the addon's independent-frame format.

## Measure a backend

| Environment | Verified scope for this implementation |
|---|---|
| Windows | Software/hardware codec round trips; Godot H.264/Opus synchronization and FEC loss; D3D12 Forward+/Mobile and Compatibility display with three reconnects |
| macOS arm64 | Software/hardware codec round trips; Godot H.264/Opus synchronization |
| Ubuntu on WSL | Software round trip and Godot H.264/Opus synchronization; hardware acceleration was unavailable |
| Android arm64 | Release build, native Auto codec round trip, and bidirectional H.264/Opus streaming with Windows on the X4000 |
| iOS arm64 | Release library, Xcode signing/installation, and bidirectional H.264/Opus streaming with Windows on the iPhone 15 Pro |

Mobile H.264/Opus tests passed on November 23, 2026, with Auto acceleration and Reliable transport. The table reports received video frames and captured audio samples. Sync p95 measures audio/video timestamp skew, not end-to-end network latency. These automated checks don't replace visual or listening checks.

| Direction | Video frames | Audio samples | Sync p95 |
|---|---:|---:|---:|
| Windows → Android | 436 | 881,664 | 16.213 ms |
| Android → Windows | 392 | 884,736 | 6.782 ms |
| Windows → iPhone | 440 | 960,512 | 8.022 ms |
| iPhone → Windows | 458 | 884,736 | 6.876 ms |

GPU capture for encoding and GPU sharing on other platforms remain unimplemented. These mobile tests use CPU frame transfer; Android Auto doesn't provide a verified hardware-acceleration flag.

Android → iPhone and iPhone → Android were also visually confirmed on November 23, 2026. The reverse direction initially displayed about 11–12 fps on Android. A bounded 20 ms MediaCodec output wait reduced output batching and frame drops. The same test then displayed about 20–24 fps, and the user confirmed the improvement. This is an observed result on these devices, not a guaranteed frame rate.

On Windows with a compatible GPU, use `--path demo --rendering-method mobile --rendering-driver d3d12 --script tests/process/gpu_video.gd -- gpu`. To test CPU transfer, use `--rendering-method gl_compatibility` and the final argument `cpu`. The test checks pixels, playback texture readback, viewport output, and reconnects.

```sh
cargo run --release --manifest-path media/Cargo.toml --example h264_probe -- software
cargo run --release --manifest-path media/Cargo.toml --example h264_probe -- hardware
cargo run --release --manifest-path media/Cargo.toml --example h264_probe -- auto
```

The probe encodes and decodes 120 generated frames, checks dimensions, colors, and keyframes, and reports wall time and process CPU time. HardwareRequired also checks backend acceleration reports. Android Auto can use hardware, but its `hardware_*` fields remain false because acceleration is unverified.

Test Godot audio/video synchronization separately:

```sh
python scripts/test_audio_processes.py --godot /absolute/path/to/Godot --codec h264 --acceleration 0
python scripts/test_audio_processes.py --godot /absolute/path/to/Godot --codec h264 --acceleration 0 --transport 2 --drop-every 11 --audio-stream
```
